Overview

Build fair play into every match

Pijon is a mobile-native anti-cheat platform for studios that need reliable signals, server-authoritative enforcement, and evidence a human reviewer can understand. It combines three layers: Core verifies the environment, Gate validates live actions, and Trace studies behavior over time.

This public guide documents the integration model and operational concepts. Exact detection thresholds, model weights, policy tuning, and incident playbooks are available only inside authenticated studio workspaces.

Designed for reviewable decisions

Pijon produces evidence and confidence signals. Studios remain responsible for player-facing actions, appeals, and compliance with local law and platform rules.

Architecture

One pipeline, three layers of trust

The client SDK collects integrity receipts and approved telemetry. Your game server attaches authoritative match context. Pijon evaluates both sources, returns decisions to your enforcement layer, and stores reviewable evidence according to your retention policy.

  1. Collect The SDK creates a session and sends signed integrity and device signals.
  2. Validate Gate compares player actions with server-authoritative rules before they affect play.
  3. Correlate Trace compares behavior across matches, devices, accounts, and skill baselines.
  4. Review Evidence is grouped into cases with reasons, confidence, and relevant match context.

Quickstart

Integrate in controlled stages

Start in observe-only mode. Confirm session coverage and server timestamps, review sample evidence, then enable assisted or automatic actions only after your team has validated false-positive performance. 

import { Pijon } from "@pijon/mobile";

const pijon = new Pijon({
  projectId: "project_live_example",
  environment: "production"
});

const session = await pijon.startSession({
  playerId: authenticatedPlayer.id,
  matchId: match.id,
  build: app.buildNumber
});

Recommended rollout

  • Use separate project keys for development, staging, and production.
  • Keep secret keys on trusted servers; never embed them in the mobile client.
  • Run observe-only for representative regions, devices, and skill levels.
  • Define appeal ownership and evidence retention before enabling enforcement.
  • Monitor version coverage so unsupported builds cannot silently bypass checks.
Core

Establish whether a session can be trusted

Core evaluates build integrity, runtime state, device trust, and session continuity. It produces signed receipts that can accompany later evidence. A Core signal should be interpreted with match context rather than used as a standalone accusation.

Typical checks

  • Build signature and version validation
  • Root, jailbreak, emulator, and unsafe-environment signals
  • Runtime tampering and memory-tool indicators
  • Session replay, signature drift, and receipt freshness
Do not expose secret material

Client identifiers may be public. Signing secrets, service credentials, and enforcement keys must remain in server-side secret storage.

Gate

Reject impossible actions before they matter

Gate runs alongside your authoritative game server. It checks movement, fire rate, hit registration, cooldowns, inventory changes, and other game-specific invariants. Each rule receives server timestamps and state snapshots so decisions remain reproducible during review. 

const decision = await pijon.gate.evaluate({
  sessionId,
  action: "weapon.fire",
  serverTime,
  state: authoritativeState,
  payload: actionPayload
});

if (decision.action === "reject") {
  return rejectPlayerAction(decision.reasonCode);
}

Use stable reason codes in player-facing systems. Internal evidence can contain more detail, but messages shown to players should avoid disclosing rules that could be reverse-engineered.

Trace

Find patterns a single match cannot prove

Trace is Pijon’s main behavioral layer. It studies aim consistency, awareness, impossible information use, coordinated accounts, repeat pairings, and changes against a player’s own baseline. Trace deliberately requires repeated evidence before recommending serious action.

Behavioral safeguards

  • Compare players with appropriate device, region, mode, and skill cohorts.
  • Separate unusual performance from evidence of prohibited assistance.
  • Reduce confidence when telemetry is incomplete or network quality is poor.
  • Route high-impact decisions through review and preserve an appeal path.
  • Recalibrate after game updates that alter movement, recoil, visibility, or input.
Evidence and review

Turn signals into accountable cases

A case groups related signals, match context, rule outcomes, confidence changes, and reviewer actions. Every state transition is recorded in an audit log. Reviewers can confirm, dismiss, escalate, or request more observation without editing the original evidence.

Status Meaning Typical next step
Observing Signals exist but evidence is incomplete Collect additional matches
Review ready Evidence passed the studio review threshold Assign an analyst
Confirmed A reviewer approved the case outcome Apply studio policy
Dismissed Evidence was insufficient or explained Retain according to policy
Webhooks

Connect decisions to studio systems

Webhooks notify your backend when cases change state, policies act, or integrations require attention. Verify every signature, reject stale timestamps, and make handlers idempotent because delivery may be retried. 

{
  "id": "evt_example",
  "type": "case.review_ready",
  "createdAt": "2026-07-08T12:00:00Z",
  "projectId": "project_live_example",
  "data": {
    "caseId": "case_example",
    "sessionId": "session_example",
    "confidence": "high"
  }
}
  • Respond with a 2xx status only after durable processing or queueing.
  • Deduplicate events using the event ID.
  • Rotate signing secrets from the authenticated studio console.
  • Alert on repeated failures and pause destructive automation if delivery is stale.
Security and privacy

Minimise data and separate responsibilities

Studios generally act as controller for player data and configure Pijon as a processor or service provider, subject to the final contract and deployment. Collect only the signals needed for anti-cheat purposes, document retention, and restrict access by role.

Baseline controls

  • TLS in transit and encryption at rest
  • Per-environment API keys with rotation and scoped permissions
  • Role-based access, multifactor authentication, and session expiry
  • Audit logs for configuration, review, export, and enforcement actions
  • Configurable retention and deletion workflows
  • Incident response contacts and breach-notification procedures
Operations

Run anti-cheat as a monitored production system

Assign owners for integration health, policy changes, evidence review, appeals, and incident response. Release game and anti-cheat changes through staging, then monitor device coverage, decision latency, webhook health, review volume, and false-positive indicators.

Suggested service indicators

  • Protected sessions as a percentage of eligible sessions
  • Gate decision latency at median and tail percentiles
  • Cases created, confirmed, dismissed, and appealed
  • SDK version and device coverage
  • Webhook delivery success and retry age
  • Policy changes and reviewer actions by role
